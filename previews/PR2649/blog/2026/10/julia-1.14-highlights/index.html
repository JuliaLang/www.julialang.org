Native code cache

Sam Schweigel

Package images let precompiled code be reused across sessions, but anything not covered by precompilation (methods specialized on your own types, code in your scripts, combinations of packages that no package precompiles) is compiled by the JIT, and until now, compiled again in every new session. Restarting Julia and running the same script meant paying the same compilation cost every time. For most workflows it matters at least as much as the first run, since the same code is run over and over in new sessions.

Julia 1.14 adds a persistent cache for JIT-compiled native code (#61527). When the JIT compiles some code, the resulting object code is stored in an on-disk database in the depot (~/.julia/cache/v1.14/), keyed on a hash of the LLVM module and everything else that affects code generation. In a later session, compiling the same code loads the object code from the cache instead of running the LLVM optimizer and code generator. Type inference still runs, so a cache hit is not free, but LLVM is typically the larger part of compilation. The cache is shared between all environments and processes using the same depot, holds 512 MiB by default (JULIA_OBJCACHE_CAPACITY), and evicts the least recently used entries when it fills up. It can be disabled with JULIA_OBJCACHE=0.

To see the effect, we ran the tasks from Julia-TTFX-Snippets, the suite that Julia's CI uses to track latency, on Julia 1.14 (Apple M4 Pro). Each task loads some packages (load) and then runs a small workload (first call), in a fresh process after the packages are precompiled. Below, the first call is measured with the cache disabled, on the first run with an empty cache, and on the second run with the cache populated by the first:

New syntax features

Labeled blocks and break with a value

Keno Fischer

@label can now create blocks that can be exited early with break name [value], and continue name continues a labeled loop (#60481). Breaking out of nested loops no longer needs a flag variable or a helper function:

function find_index(A, target)
    @label search for i in axes(A, 1), j in axes(A, 2)
        A[i, j] == target && break search (i, j)
    end  # evaluates to `nothing` if we never break
end

function first_row_without_negatives(A)
    @label rows for i in axes(A, 1)
        for j in axes(A, 2)
            A[i, j] < 0 && continue rows  # skip to the next row
        end
        return i
    end
    return nothing
end

A labeled begin block works like an expression that can return early:

port = @label check begin
    n = tryparse(Int, s)
    n === nothing && break check 8080
    1 <= n <= 65535 || break check 8080
    n
end

typegroup for mutually recursive types

Keno Fischer

typegroup blocks allow defining structs whose field types reference each other (#60569). Previously, a struct could only refer to types that were already defined, so mutually recursive types had to be broken up with an abstract supertype or a type parameter. Now they can be written directly:

typegroup
    struct Person
        name::String
        employer::Union{Company, Nothing}
    end
    struct Company
        name::String
        employees::Vector{Person}
    end
end
julia> c = Company("Acme", Person[]);

julia> push!(c.employees, Person("Alice", c));

julia> fieldtype(Person, :employer)
Union{Nothing, Company}

julia> c.employees[1].employer.name
"Acme"

Only struct and mutable struct definitions are allowed inside a typegroup. All the types are defined together at the end of the block.

Explicitly wrapping arithmetic operators

Keno Fischer

The new +%, -% and *% operators mark integer arithmetic that is intended to wrap on overflow (#50790). By default they behave exactly like +, - and *, so the point is to document intent, for example in hash functions:

function fnv1a(data)
    h = 0xcbf29ce484222325
    for b in codeunits(data)
        h = (h ⊻ b) *% 0x00000100000001b3  # overflow is expected here
    end
    return h
end
julia> typemax(Int) +% 1
-9223372036854775808

julia> 0x00 -% 0x01
0xff

This means overflow checking can catch the overflows that were not intended while leaving the deliberate ones alone. The experimental Base.Experimental.@make_all_arithmetic_checked macro makes the plain operators check for overflow (it redefines them globally, so it is intended for testing and debugging):

julia> Base.Experimental.@make_all_arithmetic_checked

julia> typemax(Int) + 1
ERROR: OverflowError: 9223372036854775807 + 1 overflowed for type Int64

julia> typemax(Int) +% 1
-9223372036854775808

Inference refines field types

Shuhei Kadowaki

After a check like if !isnothing(x.field), inference now knows the type of x.field inside the branch (for immutable structs and const fields), so the field no longer has to be copied to a local variable first (#47574).

struct Config
    timeout::Union{Int, Nothing}
end

timeout_or_default(c::Config) = !isnothing(c.timeout) ? c.timeout : 30
# Julia 1.13
julia> Base.infer_return_type(timeout_or_default, (Config,))
Union{Nothing, Int64}

# Julia 1.14
julia> Base.infer_return_type(timeout_or_default, (Config,))
Int64

The same applies after a call that can only succeed for a certain type. If only_int(::Int) is the only matching method, then after only_int(c.timeout) inference knows that c.timeout is an Int. For non-const fields of mutable structs, the field could change between the check and the use, so copying the field to a local variable first is still the way to go there.

Precompilation improvements

Ian Butterworth

  • Precompile workers and their LLVM threads now share one thread budget, which keeps cores busy without oversubscribing the machine (#61958).

  • Packages whose dependencies failed to precompile are skipped instead of being attempted (#63122).

  • Precompilation can run in a background task, with keyboard controls to cancel, detach or show progress details (#60943).

  • When loading triggers precompilation, Julia now says why, and how to avoid it.

Faster code coverage

Tim Besard

Coverage now records only whether a line ran by default, which lowers the runtime overhead. Instrumented package images can be reused across processes, and --code-coverage=@path restricts tracking to a directory tree (#62724, #62514).

As an example, here is a 2D stencil kernel, a simple summation loop, and a script that loads DataFrames.jl and runs a groupby, each run with and without --code-coverage=user (Apple M4 Pro):

1.131.13, coverage1.141.14, coverage
Stencil kernel0.08 ms0.71 ms0.08 ms0.10 ms
Summation loop0.48 ms1.56 ms0.49 ms0.47 ms
DataFrames script (total process time)0.8 s2.4 s0.7 s0.6 s

In 1.13 every coverage run recompiles the package code it calls. In 1.14 the first coverage run builds instrumented package images (about a minute for DataFrames and its dependencies) and later runs reuse them.

Multi-threading

Ian Butterworth, Jameson Nash

  • Threads.@threads works on array comprehensions like @threads [f(i) for i in 1:n] (#59019).

  • The return type of fetch(Threads.@spawn f(x)) is now inferred (#59221).

  • Threads.Atomic supports @atomic a[] += 1, and plain a[] = v is deprecated (#62382).

Better stack traces

Shuhei Kadowaki, Ian Butterworth

Inlined frames now show full method signatures (#53925):

Errors raised during package loading no longer show the internals of the code loading machinery (#52988).

New library features

  • StringView (ported from StringViews.jl) wraps a byte vector as a UTF-8 string (#60526).

  • readdir(path, DirEntry) and the lazy eachentry(dir) return entries together with their file type (#55358, #62164).

  • tap(f) and unsplat(f) function helpers (#61340, #62714).

  • Dates: nanosecond-precision Dates.Timestamp and the n format code for fractional seconds (#62994).

  • TOML: comments can be preserved when parsing and printing a file (#62672).

  • Test: @test accepts a context keyword that is shown on failure (#60501).

  • InteractiveUtils: @methods f(args...) lists all methods applicable to a call (#62311).

  • Markdown: behavior is much closer to CommonMark, including raw HTML and strikethrough.

REPL

  • Tab completion of Module.<TAB> lists public names first (#63601).

  • using A, B, C precompiles all packages in one parallel session.

  • The REPL emits OSC 133 "semantic prompt" markers (#63112). These invisible escape sequences tell the terminal where each prompt, input and output begins, the same way shells like zsh and fish do. In terminals that support them (e.g. VS Code, iTerm2, kitty, WezTerm, Ghostty and Windows Terminal), you can jump between previous prompts in a long REPL session instead of scrolling, select or copy the output of a single command, and in VS Code, copy a command together with its output. Terminals without support ignore the markers, and they can be turned off with repl.options.semantic_prompts = false in an atreplinit hook in startup.jl.

  • -P is a shorthand for --project (#59867).

JuliaLowering

Em Chu, Claire Foster

THE DEFAULT MIGHT CHANGE

JuliaLowering, the new lowering pass written in Julia, now ships compiled into Julia. The old flisp lowering is still the default; JuliaLowering can be enabled with JULIA_USE_FLISP_LOWERING=false (#63614).

JuliaC/trim

Gabriel Baraldi, Cody Tapscott

Julia now installs a static libjulia-internal.a, so JuliaC.jl can link a trimmed program into a single executable (#63618). Libdl.LazyLibraryCallback makes lazy library callbacks work under --trim.

Build

LLVM 23

Tim Besard

Julia has been upgraded to LLVM 23 (#63626). Besides the usual improvements to code generation, LLVM 23 is also faster at compiling code itself, which directly reduces latency in Julia. On the TTFX benchmark suite, precompilation got about 4% faster and the first call into freshly loaded packages about 3.5% faster (geometric mean over 38 workloads).

Julia is not the only one seeing this. The Rust compiler also saw an unexpectedly large improvement from LLVM 23. Thanks to the LLVM developers who have spent so much effort on making LLVM itself faster over the past releases!

Build variants

TODO: authors

Besides the standard binaries, Julia 1.14 is released in two variants that previously only existed as nightlies or had to be built from source:

VariantWhat is differentPlatformsjuliaup channel
Optimized (+opt)Built with PGO and ThinLTO, plus BOLT on LinuxLinux (x86-64, i686, aarch64), macOS (x86-64, Apple silicon), Windows (x86-64)1.14+opt, release+opt
Assertions (+assert)Assertions enabled in the runtime and in LLVMLinux (x86-64)1.14+assert, release+assert

The optimized build is built with make -C contrib/optimized (#63179), which builds Julia and LLVM in two stages. The first stage is instrumented and is used to build the system image and the stdlib package images, which records a profile of where the compiler spends its time. The second stage is built with profile-guided optimization (PGO) using that profile and with ThinLTO. Since LLVM is built from source in both stages, libLLVM gets PGO and LTO too, which matters for latency since a large part of compilation time is spent in LLVM. On Linux x86-64 and aarch64, libLLVM, libjulia-internal and libjulia-codegen are then additionally optimized with BOLT, which reorders the machine code based on a profile from the same workload (#62725, #63162, #63214, #63312). The optimized build makes compilation faster across the board. The 1.14+opt rows in the latency chart above show how much.

The assertion build has the C/C++ assertions in Julia's runtime and LLVM's assertions enabled, and verifies the LLVM IR after Julia's own LLVM passes. It is slower than the standard build, but when Julia crashes or miscompiles something it often turns the problem into a failed assertion close to the actual bug. If you hit a segfault or an internal error, checking whether it reproduces on the assertion build and including the result in the bug report is very helpful.

The easiest way to install a variant is with juliaup, where it installs next to the standard build:

juliaup add 1.14+opt
julia +1.14+opt

The binaries can also be downloaded directly, e.g. https://julialang-s3.julialang.org/bin/linuxopt/x86_64/1.14/julia-1.14.0-linuxopt-x86_64.tar.gz (macosopt and windowsopt for the other platforms). TODO: link from the downloads page. The macOS app and the Windows installer of a variant are named e.g. Julia-1.14-opt, so they also install next to the standard build. The REPL banner and versioninfo() show which variant is running, e.g. Version 1.14.0+opt (#64024).

Optimized and assertion builds are also available as nightlies (juliaup add nightly+opt).

RISC-V builds

Tim Besard

Julia 1.14 comes with prebuilt binaries for 64-bit RISC-V Linux (rv64gc), for both releases and nightlies. TODO: download link. The binaries are cross-compiled on x86-64 machines, with the parts of the build that run Julia (system image, package images and docs) running under QEMU.

1.14 also fixes a range of RISC-V issues (#62951, #62995): ccall now passes and returns structs correctly according to the native ABI, hardware fma is detected and used, and @code_native highlights RISC-V assembly and shows branch targets as labels.

Since CI has no RISC-V hardware, the builds are not tested and RISC-V remains a Tier 3 platform. Bug reports from people running Julia on RISC-V are very welcome.

Smaller Julia installation and package images

Kristoffer Carlsson

A Julia installation takes up considerably less disk space in 1.14, as do the package images of the packages you install. Most of the savings come from shrinking debug info while keeping Julia stack traces unchanged:

  • The C/C++ runtime is built with line tables only (#63641). Together with the compression below, libjulia-codegen shrinks from 84 MiB in 1.13 to 6 MiB on Linux, and from 122 MiB to 15 MiB on Windows.

  • Code in the system image and in package images gets only line tables as well (#63937). Julia already rebuilds inlined frames in stack traces from its own debug info, so the inlining information in DWARF was mostly unused. On Linux, the debug info in the system image goes from 73 MiB to 20 MiB. As a bonus, the first stack trace in a session is printed about twice as fast and uses about 40 MiB less memory. External tools like gdb and perf no longer see inlined frames in precompiled code.

  • Julia emits DWARF 5, which has more compact debug info than DWARF 4 (#63639).

  • On Linux and FreeBSD, debug sections of package images, Julia's own libraries and bundled libraries are compressed (#63642, #63640, #63687, #63810). Combined with the line tables above, the debug info in the bundled stdlib package images drops from 54 MiB to 5 MiB.

  • The stdlib package images compiled with --check-bounds=yes are no longer bundled. Since Pkg.test no longer forces bounds checking (as of 1.13), these are rarely needed, and they are now distributed as a separate archive (#60054).

The chart below shows the size of an unpacked Julia installation, split by component. Use the buttons to look at the download size or at a single component, and hover over a bar for its size. The installation is about a third smaller than 1.13 on all three platforms and close to the size of 1.10 again.

The savings also apply to the package images of packages you install. For example, on Linux an environment with DataFrames, CSV, Plots, OrdinaryDiffEq and JuMP (329 package images) takes up 659 MiB of precompile cache, compared with 859 MiB on 1.13. The debug info in those package images drops from 106 MiB to 8 MiB.

Pkg

Kristoffer Carlsson, Ian Butterworth, Stefan Karpinski, others

Faster first Pkg operation

Previously, the first time a session used the registry, Pkg had to decompress the whole registry tarball and walk its ~75k entries with Tar, creating a string for every file in it, even though only a few packages were needed. The registry is now cached on disk in a binary format with a per-package index, and memory-mapped so that a session only reads the packages it uses. This makes the first Pkg operation in a session noticeably faster (Pkg#4797). For example, the first Pkg.status() in a fresh session for a project with a single dependency, on Julia 1.13:

julia> using Pkg

julia> @time Pkg.status()
Status `~/ex/Project.toml`
  [7876af07] Example v0.5.5
  0.150727 seconds (1.27 M allocations: 93.000 MiB, 32.88% gc time, 8.05% compilation time)

and on Julia 1.14:

julia> using Pkg

julia> @time Pkg.status()
Status `~/ex/Project.toml`
  [7876af07] Example v0.5.5
  0.045183 seconds (223.04 k allocations: 13.359 MiB, 39.54% gc time, 5.67% compilation time)

[compat-overrides]

A new project file section replaces all compat constraints on a package, for example to try a new version that a dependency does not allow yet (Pkg#4841).

pkg> add --from

Adds the direct dependencies of another environment, e.g. to populate @v1.14 from @v1.13 (Pkg#4777).

Lazy add/update

Pkg.add, Pkg.update and Pkg.resolve accept lazy=true to update the project and manifest without installing anything.

Pkg.why prints a tree

Pkg.why now prints a dependency tree instead of listing every path, which could run to thousands of lines (Pkg#4839). Here is why PrecompileTools ends up in an environment with CSV and DataFrames:

(whyenv) pkg> why PrecompileTools
  PrecompileTools
  ├─← CSV
  ├─← DataFrames
  ├─← Parsers
  │   └─← CSV
  ├─← PrettyTables
  │   └─← DataFrames
  └─← StringManipulation
      └─← PrettyTables (*)

Each package's dependents are listed only once, and later occurrences are marked with (*), which keeps the output small even when there are many paths. With --forward the same information is printed starting from the project's direct dependencies instead:

(whyenv) pkg> why --forward PrecompileTools
  CSV
  ├─→ Parsers
  │   └─→ PrecompileTools
  └─→ PrecompileTools
  DataFrames
  ├─→ PrecompileTools
  └─→ PrettyTables
      ├─→ PrecompileTools
      └─→ StringManipulation
          └─→ PrecompileTools

Environment IDs in manifests

Manifests now record an environment_id, which Julia uses in precompile cache file names so that environments at the same path (e.g. in containers sharing a depot) no longer overwrite each other's caches (Pkg#4824).

Other changes

  • Pkg.instantiate(; update_on_mismatch=true) falls back to updating when the manifest is stale (Pkg#4678).

  • Pkg.activate warns when loaded packages differ from those in the new environment (Pkg#4679).

  • Artifact selection hooks can load their package's dependencies (Pkg#4747).

Bugs found by formalizing Base in Lean

Miles Cranmer

During the 1.14 release cycle, Miles Cranmer modelled parts of Base in Lean 4 with the help of AI agents. Each Julia function gets a Lean definition that follows the source line by line, including integer wraparound and which exceptions get thrown. Properties taken from docstrings and the manual are then stated as theorems for the agents to prove. When a proof fails, the counterexample usually points to a bug, which only counts once a plain Julia script reproduces it. The models, the properties and all bugs found are in the julia-in-lean repository.

So far this has found around 400 bugs. Many of them are edge cases at typemin, empty collections or unsigned types. For example, reverse negates the step of a range, and negating typemin(Int8) wraps back to itself:

julia> r = Int8(0):typemin(Int8):typemin(Int8)
0:-128:-128

julia> length(r), length(reverse(r))
(2, 0)

The ones that seemed worth a maintainer's time were filtered by hand, checked for duplicates and filed as issues by @MilesCranmerBot. Fixes for many of them, also from @MilesCranmerBot, were merged, most of them marked for backport to 1.14. They cover things like deleteat!, partialsort, LinearIndices, maximum with dims on all-missing arrays, circshift! on an empty BitVector, BigFloat parsing, and the TOML parser. The approach also found a miscompilation that was introduced during 1.14 development, where inference reused an isa check from an earlier loop iteration.

We are excited about combining formal methods with AI to find bugs, and we hope this effort continues and catches more severe bugs in the future.
